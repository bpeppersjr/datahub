# CMS hospital production input pinning

This connects the already implemented typed registry admission to existing standalone production CLI/planner interfaces. It does not perform an acquisition, production plan creation, production run, pointer change or catalog-nine migration during implementation/testing.

`scripts/reconcile-business-production.mjs plan --cms-hospital-selection config/cms-hospital-retained-selection.json` is the proposed user-facing entry when a future production plan is requested. Run/stop modes reject the option: execution reconstructs it only from its pinned plan. `scripts/build-business-registry.mjs` forwards the same explicit option to `cmsHospitalSelection`. Missing/repeated options reject. No Ohio source is required.

`cms-hospital-production-input.mjs` replays the native retained admission input, pins the config selection plus the exact twelve-file source job roster, then replays/rechecks source declaration, directory roster and every byte/hash pin. The thirteen evidence pins include manifest, intent, all four request intents, both metadata snapshots, notice, raw CSV, selected JSONL and emitted policy. No sibling jobs, current-source pointers or downloads are used. Runtime source policy is compiled and bound through its emitted artifact; source-policy config documentation is included in implementation/config pins, not treated as a mutable override.

For this new optional plan only, the conservative implementation inventory includes all runner/scripts/config modules and package/lock files, covering dynamic/transitive verifier imports. Existing absent/undefined-option plan shape, ordering and fingerprints are unchanged. Combining with existing retained childcare/MN inputs uses the same sorted deduplicated inventory; CMS remains a separate `cmsHospitalPin`, not a new member of the unrelated four-source childcare enum.

Source pins are checked before/after every stage. Run-time replanning reproduces the CMS selection and immutable declaration. Registry emission must contain the exact CMS dependency and full declaration, not merely a matching source ID. The ordinary independent registry-verification stage then replays selected source membership/policy. Adding CMS to benchmark/resolution historical recovery is rejected: those existing outputs did not contain this admission. Historical plans/receipts are not rewritten. Stop behavior remains the existing controller's cooperative stage-boundary behavior.

The pin explicitly declares `admissionScope: typed-registry-directory-rows-only` and `coverageProjectionImplemented:false`. Eight existing production stages remain; a successful future run would establish registry admission and unchanged legacy coverage behavior, not hospital coverage visibility or nine-source percentages. A distinct coverage/catalog migration and consumer adoption are still required. No fixture SUCCEEDED receipt is production evidence.

Tests: CLI missing/repeated/mode rejection; native-root rejection; optional gated retained thirteen-file/implementation-roster validation without plan creation; mocked-source controller fixture with actual planner/reconstruction/execution bookkeeping, absent-option compatibility, forwarding, historical recovery rejection, pre-stage evidence mutation, rehashed pin mutation, missing dependency, changed output declaration, mid-stage source drift and success. Source-helper mocking is explicitly synthetic controller proof, separate from the actual retained pin validation and earlier actual registry builder/verifier test. No application UI/server/managed-operation changes occur here.

The additional tracked controller test `CMS and MN co-selected planner binds both rosters and declarations without fingerprint collisions` exercises both inputs together. It asserts separate evidence rosters and declarations, each forwarded exactly once, deduplicated implementation pins, distinct stable plan fingerprints for CMS-only/MN-only/combined inputs, rejection when either selection changes, rejection when either emitted dependency/declaration is wrong or missing, rejection of both historical recovery modes, and all eight synthetic stages succeeding only with both correct declarations. Co-selected execution checks the MN declaration as well as the CMS declaration; old plans without CMS retain their existing behavior. No synthetic plan or SUCCEEDED fixture is presented as production adoption.
