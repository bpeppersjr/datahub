# Governed business flat-file export

`scripts/compose-flat-business-export.mjs` writes selected national business-registry location evidence to CSV, JSONL, or both under the `flat-business-export@1.1.0` contract. Every row explicitly declares `cohort_kind` (`matching-profile` or `reporting-only`) from its retained artifact type, and preserves source record/profile/site identity, exact source artifact path, row-level qualification, and applicable source-policy provenance. Matching profiles and reporting-only sites remain separate row units.

Example local-review export:

```powershell
node scripts/compose-flat-business-export.mjs --category retail-consumer --state TX --field business_name,street,city,state,zip_code,zip4,geocode --policy-mode local-review
```

The default `public-only` mode emits only the explicitly recognized record policies `public`, `public-open-ny-terms`, and `public-factual-fields-with-source-limitations`. Any missing, unknown, restricted, or local-review policy is rejected. `--policy-mode local-review` must be explicitly supplied to include `local-review-only` records; it still rejects unknown or more restrictive policies. These files remain local artifacts and are never a public publication action.

Category IDs and source IDs match `runner/business-map-store.mjs`. ZIP5 and ZIP+4 are separate columns, and coordinates are emitted only as a validated `geocode` object or null. Combined ZIP+4 postal strings and raw `location`, `geometry`, or polygon fields are rejected. CSV values beginning with spreadsheet formula-control characters are prefixed with an apostrophe; ZIP strings retain leading zeroes. Selected columns always gain the mandatory row-provenance fields so every row remains traceable.

The `tax-exempt-organizations` category remains cataloged, but a row cannot be emitted unless its exact source-policy provenance is present in the selected governed evidence. The current matching-profile policy inventory does not cover the synthetic IRS fixture used by legacy tests, so that fixture fails closed rather than standing in for retained source lineage.

Each input must be a published governed pointer or release manifest. Every input artifact is checked against its declared byte count and SHA-256 before acceptance. Registry 2.13 reporting checksums cover the exact compressed bytes subsequently decoded with strict UTF-8. Output is written beneath `datahub`, using stream backpressure. CSV/JSONL and summary hashes are recorded in `manifest.json`; the manifest also hash-binds the selected registry, lifecycle, entity-geography, reporting-only qualification, and source-policy provenance registrations/releases/artifact inventories. It records nonadditive evidence semantics (`entity_resolution_applied:false`, `current_operation_verified:false`, `active_business_eligible:false`, `unique_business_count:null`, USPS validity unverified). The manifest is atomically renamed into place last. On compose failure the incomplete run directory is removed.

Tennessee childcare is included in the `childcare` source group only from exact registry 2.13 reporting evidence. Its source-release dependency, artifact partitions, accepted row count and missing-ZIP reasons must reconcile even when filters or public-only policy exclude rows from output. Missing ZIP5/ZIP4 stay null; source `street2` is preserved as `unit_or_additional`. Select `source_status`, `source_evidence` and `identity_matching_eligible` to retain explicit recovery/status detail; those fields are included by default. All Tennessee rows remain local-review-only and ineligible for matching. This capability does not imply Tennessee has been promoted into the current production registry.

Run `node --test runner/business-flatfile.test.mjs runner/flat-business-export-verifier.test.mjs` for offline contract coverage. The Windows launcher is `export-business.bat`; invoking it without arguments shows help. `npm run business:export -- <options>` is equivalent. Exports read source releases without modifying them; the current implementation scans every profile partition even when selecting one state.

Verify completed outputs with `npm run business:export:verify -- <manifest-path> [--expected-sha256 <manifest-sha>]`. The strict v1.1 verifier independently checks exact selected registrations and release/artifact hashes, all row cohort/policy/qualification invariants, conservation/filter semantics, single-link bounded artifacts, and canonical JSONL/CSV row equivalence. Managed export operations must pass this verifier before becoming `SUCCEEDED`; downloads reverify the exact manifest and artifact hashes. The operation API exposes verified SHA-256 values and downloads carry artifact/manifest digest headers. A well-formed file alone does not establish business accuracy, unique businesses, current operation, USPS validity, or national completeness.

The September 7, 2026 pre-v1.1 New York export remains historical output and is not evidence that it satisfies this stricter lineage contract. A large-stream regression verifies more than eleven backpressure cycles without accumulating error listeners.
