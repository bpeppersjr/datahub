## Priority 2: a typed local-review export

`scripts/compose-flat-business-export.mjs:profileArtifacts` selects only location-profile or reporting-location `.jsonl.gz` artifacts. The Minnesota credential artifact is a distinct uncompressed `.jsonl` type, so it is not selected. Its category/field roster and `runner/business-flatfile.test.mjs` contain no credential export contract. `scripts/verify-flat-business-export.mjs` validates generic flat-business rows, not typed credential provenance and exclusions.

There is also an existing default-export compatibility gap: the composer accepts Tennessee registry reporting only for versions `2.13.0`/`2.14.0`; current registry `2.15.0` has a Tennessee dependency and therefore fails its exact dependency/version gate. This is a separate existing-consumer compatibility task. Do not widen that gate casually to implement Minnesota export, and do not route credentials through location profiles.

A minimal independent implementation can add `runner/mn-credential-flat-export.mjs`, `scripts/export-mn-credentials.mjs`, and focused tests, explicitly selecting the verified credential artifact/release. Alternatively extend the existing composer/verifier with an explicit credential evidence mode, but preserve default business-export semantics and repair supported version pairing deliberately. App-managed export registration, if desired, is a separate explicit handoff in `runner/managed-operations.mjs` and its export catalog/UI; ordinary business row counts must not silently include credentials.

Required typed projection: release-scoped source-row ID, typed `minnesota_dli_construction_credential` identifier, credential kind/category, publisher status and original unparsed dates, publisher-reported address with separate ZIP5/ZIP4, source/release/observation/ingest provenance, transformation version, policy and typed record unit. Preserve repeated credential numbers; never deduplicate them into businesses. Coordinates, county/ZCTA assignment, canonical site/entity IDs and verified active-business claims must remain absent/null or explicitly false as appropriate. Require `local-review-only`; reject public export. Write a distinct credential artifact type and `credential_rows_written` summary, not a business-count claim. Verify hashes, exact source row conservation, policy, and selected fields independently; handle cancellation and manifest-last publication using existing bounded I/O. The existing 150 MB/250,000-row credential loader bounds are reusable for future offline implementation; this audit did not run that loader.

## Map adoption boundary

`runner/business-map-store.mjs` has no credential category/projection. `countsFor` sums existing category fields into `all`, so simply adding a credential field there would contaminate aggregate business-evidence counts. Its name drilldown reads location-profile and childcare reporting-location partitions, not credentials. `runner/business-map-compatibility.mjs` already supports current coverage `2.11.0` paired with registry `2.15.0` for existing reporting; the missing work is explicit credential semantics, not another production build.

Use a distinct reported-state/reported-ZIP credential view with cohort denominators and missing/unrepresented-ZIP accounting. Do not render provider points, infer county membership, assign ZIP centroids, or treat reported ZIP grouping as governed ZCTA membership. County credential counts are null by contract. If integrated into map controls, change `runner/business-map-store.mjs` and its tests plus the consuming coverage UI deliberately; preserve existing `all` counts and physical-location drilldown. The already implemented retained panel may be the safer first surface while typed export is completed.
