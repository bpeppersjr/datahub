# Florida FDACS retail-food offline lifecycle

`fl-food-retail-acquisition@1.0.0` is registered as an offline-fixture-only, acquisition-blocked connector. It does not replace or broaden the separately governed `fl-food-gis-preflight@1.0.0` metadata service. It has no allowed network host, native transport, production queue registration, scheduler, current-pointer update, or public export path.

The connector exists to prove the record contract and failure boundaries before provider-record use is authorized. Its only entry point accepts an in-memory `Map` of injected response fixtures. The fixture keys must match the fixed metadata, portal-notice, count, ID, and page itinerary generated by the source contract. No URL, fetch function, headers, credentials, source override, or retry option is accepted.

## Durable evidence

Each invocation creates one UUID directory below `data/tmp/fl-food-retail-offline/jobs` unless a test supplies another app-contained root. Intent and the exact blocked policy are written first. Every injected response is retained with its digest, followed by the synthetic selected JSONL and ordered receipts for preflight, plan, acquire, validate, normalize, reconcile, quality gate, publish, and finalize. The publish receipt explicitly says no dataset was published and no current pointer was updated. The manifest is created last with exclusive creation, then independently verified without network access.

Failure or cooperative cancellation retains a redacted `failure.json` and never creates `manifest.json`. A fault immediately before manifest creation proves that completed stage receipts cannot be mistaken for publication. The verifier rejects a wrong manifest hash, policy drift, artifact tampering, missing or additional files, symbolic-link entries, excessive recorded usage, a changed stage sequence, or any claim of native acquisition, public export, provider records, or production dispatch.

## Enforced fixture limits

| Limit | Value |
| --- | ---: |
| Fixture reads | 112 maximum |
| Source records | 50,000 maximum |
| Page rows | 500 maximum |
| Pages | 100 maximum |
| Metadata response | 1 MiB maximum |
| Count response | 20,000 bytes maximum |
| ID response | 2 MiB maximum |
| Page response | 2 MiB maximum |
| Total injected responses | 128 MiB maximum |
| Selected JSONL | 256 MiB maximum |
| Parallel operations | 1 |
| Native requests | 0 |
| Redirects and retries | 0 |

The underlying contract still verifies exact before/after metadata and portal notice bytes, stable before/after count and sorted object-ID inventory, one response row per requested object ID, explicit selected fields, separate ZIP5 and ZIP4, and optional WGS84 point syntax. Publisher points remain unverified and ineligible for county assignment. `FE_TYPE` remains opaque, current operation remains unverified, identities remain unreconciled, and unique-business/national-completeness claims remain null.

## Blocked prerequisites

Native record acquisition remains prohibited until a separate review approves the provider-record use and redistribution basis, a publisher-documented `FE_TYPE` codebook, currentness and edition semantics, an acquisition plan, and explicit operator authorization. Enabling those prerequisites requires a new reviewed implementation; changing fixture configuration cannot enable provider access.
